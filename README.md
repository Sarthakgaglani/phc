# ProjectH

A federated-ready health resource and supply-chain platform for India's
Primary Health Centres (PHCs). It predicts medicine shortages before they
happen and recommends safe, human-approved redistribution between PHCs —
without ever creating a new shortage at the donor.

**Core value proposition:** detect shortages before they happen, and
recommend safe redistribution without ever creating a shortage at the donor
PHC. The core application works correctly with zero LLM calls — AI (Gemini)
is optional and additive, never load-bearing.

---

## What It Does

The system runs a continuous eight-step cycle:

1. **Observe** — PHC staff record stock movements against an append-only
   inventory ledger.
2. **Forecast** — a deterministic (no LLM) demand forecast runs per
   PHC/medicine.
3. **Detect risk** — Days of Cover and shortage are computed against
   configurable safety-stock/threshold rules, and alerts fire automatically.
4. **Recommend** — a shortage is matched against every other PHC's *safe
   surplus* (never just "who has more"), split across donors if needed, and
   explained (why this donor, what it costs them, what changes for them).
5. **Approve** — a district/state officer reviews and approves or rejects
   the recommendation. Nothing moves without human approval.
6. **Transfer** — dispatch and receipt are tracked through a state machine
   with optimistic locking and idempotent retries, safe under concurrent
   multi-user access.
7. **Update inventory** — receipt writes the transfer into the same ledger
   every other stock movement goes through.
8. **Measure outcome** — did the transfer actually prevent the predicted
   stock-out? Tracked and surfaced on the State dashboard.

Everything above is computed in plain Python and is fully functional with
no AI service reachable. Gemini, where enabled, only narrates
already-computed numbers in plain language (summaries, multilingual
explanations, a constrained natural-language query) — it never calculates
stock, shortage, surplus, Days of Cover, or transfer quantities.

## Current Data: All PHCs Use Seed Data

> **Important:** The system currently runs entirely on **synthetic seed
> data** generated by the management command
> [`seed_data.py`](backend/core/management/commands/seed_data.py). There is
> no live data ingestion pipeline yet.

Running `python manage.py seed_data` creates:

| Entity | What's seeded |
|---|---|
| **Geography** | 1 synthetic state ("Uttar Pradesh (synthetic)"), 3 districts (Bareilly, Shahjahanpur, Pilibhit), 10 PHCs with deterministic lat/lon coordinates |
| **Users** | 1 demo user per role — `demo_phc` (PHC staff), `demo_district` (District officer), `demo_state` (State admin) |
| **Medicines** | 4 medicines: ORS packets, Paracetamol 500mg, Amoxicillin 250mg, Iron folic acid |
| **Inventory** | Opening balances for all 4 medicines across all 10 PHCs (varied by a deterministic formula: `base_qty + (index * 37) % 200`) |
| **Operations** | Bed capacity, patient footfall, and staff attendance seeded for today's date across all 10 PHCs |
| **Config** | A default `RiskConfig` row with platform-wide safety-stock, forecasting, and risk-threshold parameters |

The command is **idempotent** — re-running it via `get_or_create` never
duplicates rows or touches non-synthetic data. Every seeded name includes
"(synthetic)" and must never be presented as real government data.

After seeding, `python manage.py recompute_risk` runs the full
Forecast → Risk → Alert → Redistribution Recommendation pipeline
across all seeded PHCs to bring the system into a demo-ready state.

## How Medicine Redistribution Works (PHC A → PHC B)

The system **does** implement end-to-end medicine deduction and transfer.
Here is the exact code path:

### Step 1: Detect shortage at PHC B

The forecasting service computes per PHC/medicine:

```
Required Stock = Predicted Demand + Safety Stock
Shortage       = max(Required Stock − Current Stock, 0)
```

If PHC B has a shortage > 0, the system proceeds to donor matching.

### Step 2: Find safe donors (e.g. PHC A)

[`donor_matching.py`](backend/transfers/services/donor_matching.py) is a
**pure function** that ranks every other active PHC by:

1. **Distance** (closer first — lower transport risk)
2. **Safe surplus** (larger surplus first — fewer donors needed)
3. **Predicted daily consumption** (lower consumption = safer long-term)
4. **FEFO** (First Expiry, First Out — tie-break, stub until batch tracking)
5. **PHC id** (deterministic final tie-break)

Each donor's contribution is **capped at two independent hard limits**:

- **Safe Surplus cap:** `max(Current Stock − Required Stock, 0)` — never
  transfers more than the donor can spare after covering its own demand +
  safety stock.
- **Min Days of Cover cap:** `max(Current Stock − (min_days_of_cover ×
  daily_consumption), 0)` — never drops the donor below the configured
  minimum Days of Cover.

The tighter of these two caps applies. A shortage may be **split across
multiple donors** — no single donor is ever forced to give more than its
safe surplus.

### Step 3: Approve (human-in-the-loop)

A `TransferRecommendation` is created with full explainability data
(recipient's shortfall math, each donor's stock/surplus/Days of Cover
before and after). A district/state officer reviews and **approves or
rejects** it. Nothing moves without explicit human approval.

### Step 4: Dispatch → Receive → Inventory update

The state machine in
[`state_machine.py`](backend/transfers/services/state_machine.py)
tracks: `PENDING_REVIEW → APPROVED → DISPATCHED → RECEIVED`.

On **receipt** (and only then), the system atomically writes two
`InventoryTransaction` rows in a single database transaction:

```python
# Deduct from donor (PHC A)
record_transfer_out(donor_phc, medicine, quantity, ...)  # writes −quantity

# Credit to recipient (PHC B)
record_transfer_in(recipient_phc, medicine, quantity, ...)  # writes +quantity
```

This is **the only place the system itself writes to the inventory ledger**
rather than manual entry. Both rows are written atomically with the status
transition so the ledger and transfer state can never disagree.

### Step 5: Measure outcome

After receipt, `record_immediate_outcome()` captures whether the
recipient's risk level actually improved — did the transfer avert the
predicted stock-out? This is surfaced on the State dashboard.

## Stack

- **Frontend:** React + TypeScript, one app, role-based routing (PHC /
  District / State)
- **Backend:** Django + Django REST Framework
- **Database:** PostgreSQL
- **Async/real-time:** Celery + Redis, Django Channels for live push
- **Optional AI:** Gemini API (summaries/explanations only)
